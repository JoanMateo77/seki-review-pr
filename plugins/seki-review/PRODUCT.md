# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

- **Author:** whoever opens the PRs of a project with several repos and per-environment branches (for example backend, checkout and several portals). Opens the dashboard to decide what to do today: what to merge into testing, what to promote to production, what got blocked or has no counterpart.
- **Reviewer:** another team member who reviews those PRs separately, without having written the code. Needs to understand each change (what it solves, why, how to test it) and record a decision.

## Product Purpose

Seki Review: a local PR review dashboard generated by the `seki-review` plugin. It brings together in a single view the real status of each PR against testing and production, the automatic verifications and the explanation of the change. Success: the author knows within a minute what to do today, and the reviewer understands and decides on a PR without opening the full diff.

## Positioning

Unlike GitHub's PR list, it checks with git whether the code is already in testing or in production, knows the sibling branches of each portal and applies the project's own rules, each one with the incident that originated it.

## Operating Context

- Local HTML file (`revision-prs/tablero.html`) opened in the browser. Never published online; shared as a file.
- Regenerated from Claude Code with `/seki-review:review-prs`; the data is a dated snapshot.
- Used at the office, on a laptop, during the workday; short, repeated sessions.

## Capabilities and Constraints

- Self-contained HTML, no build or dependencies; only Mermaid is loaded from the CDN, and without network the text is shown.
- What the reviewer marks lives in their browser; to hand it back to the author it is exported and imported as a file.
- With the dashboard served, approving a change proposal commits and pushes to the PR's branch: it is the only write to GitHub. It never merges or posts comments.
- UI text in formal, impersonal English, no emojis; each project's own text rules go in its `contexto`.

## Product Principles

1. Action first: the queue order says what to do, not what exists.
2. Evidence before opinion: each status says how it was checked.
3. The reviewer needs no prior context to decide on a PR.
4. Nothing leaves the machine unless someone sends it on purpose.

## Future improvements

- **Rules for review templates (PCI DSS and others), noted 2026-10-28 from the ai-coding wiki.** Each item
  of a template carries cited evidence (file and line) or the status "not verifiable from the diff"; checking an item
  is not the same as having seen the behavior. Whatever can be checked with a fixed rule goes to `pr_verificaciones`,
  not to the model. The same template is not run with several models hoping for consensus: agreement between models gives
  hints, it does not rule out shared mistakes. In "My reviews", Approve or Request changes on GitHub is a human
  action for each submission, with the diff open.

- **Shared templates (noted 2026-10-27, not implemented).** Several base review templates (PCI DSS-style
  security, OWASP web, SQL/DDL migration, screens and copy, integrations, lightweight) that can be shared
  from a repository instead of living only in each machine's `~/.config/seki-review/plantillas/`. This means
  versioning the templates and making the project configuration independent of machine-specific paths.
